# round-collector output schema

What `round-collector` writes, what the values mean, and the conventions you
must know before aggregating anything. Written for whoever is reading the CSVs,
not for whoever is editing the Go.

Generated by `round-collector -demo <path>`. Output lands in
`<out>/<demo-basename>/`.

```
manifest.json        run metadata: map, tick rate, counts, column lists
players.csv          steamid -> last-seen name
rounds.csv           one row per round
round_players.csv    one row per (round, player)
ticks.csv.gz         one row per (round, tick, player)   <- the big one
```

Reference numbers from a 667 MB, 48-round overtime demo: **3,160,237 tick rows,
49 MB gzipped, ~25 s to produce.**

## Read it with

```sql
-- DuckDB reads .csv.gz natively
SELECT * FROM 'out/mega_ot_mirage/ticks.csv.gz' WHERE round = 5 AND phase = 'live';
```

```python
import pandas as pd
ticks = pd.read_csv("out/mega_ot_mirage/ticks.csv.gz")   # gzip inferred
```

## Five things that will bite you

**1. Filter `is_alive = 1` before aggregating any state column.** Dead players
keep emitting rows until the round ends, frozen at their last living values. Of
836k dead rows in the reference demo, 643k carry a non-zero `buttons` mask and
427k carry non-zero `shots_fired` — a corpse reads as holding W for thirty
seconds. Only `health`, `armor`, `is_alive` and `vel_valid` update after death.
Any button-frequency or shots-fired aggregate that skips this filter is roughly
a quarter garbage.

**2. `buttons` lags position by exactly one tick.** It is sourced from
`m_nButtonDownMaskPrev`, the *previous* command's mask. For counterstrafe work —
which is precisely about the tick-level relationship between a key release and
velocity reaching zero — that systematic one-tick offset matters. Account for it
rather than discovering it.

**3. `vel_valid = 0` means "no usable predecessor," not "speed was zero."**
Velocity is derived by differencing consecutive positions, so the first sample
of each player in each round, and any sample after a gap of more than 8 ticks,
has nothing to difference against. Those rows report `speed = 0.00` because
there is no answer, not because the player was stationary. Always filter
`vel_valid = 1` before reasoning about movement.

**4. `yaw` wraps at ±180.** The observed range is `[-180, +180]`, not 0–360
(demoinfocs' own documentation says 0–360 and is wrong). Angular deltas need
wrap handling or you will get 350-degree flicks that were really 10-degree ones.

**5. `phase` is three values and you almost always want one.** `freeze` is
players frozen at spawn (position is constant and useless for movement,
retained because buy decisions happen then), `live` is real play, `postround` is
after the win condition when movement and kills carry no analytical weight.

## ticks.csv.gz

One row per `(round, tick, steamid)` — that triple is unique and is the primary
key.

| Column | Type | Meaning |
|---|---|---|
| `round` | int | 1-based round number |
| `tick` | int | ingame server tick (not demo frame) |
| `phase` | enum | `freeze` \| `live` \| `postround` |
| `steamid` | uint64 | join key to `players.csv` |
| `team` | int | 2 = T, 3 = CT. On the row because it changes at halftime |
| `x`, `y`, `z` | float | world position, Hammer units (1 unit = 0.75 inch) |
| `yaw`, `pitch` | float | view angles, degrees. Yaw wraps ±180 |
| `vel_x/y/z` | float | units/sec, derived by differencing |
| `speed` | float | XY magnitude, units/sec. **Excludes Z** so a jump does not read as movement |
| `vel_valid` | 0/1 | whether the velocity columns are meaningful |
| `accuracy_penalty` | float | active weapon's live inaccuracy; rises when firing/moving, decays as it settles. Full precision — the useful signal is at the low end |
| `buttons` | uint64 | raw input bitmask. **One tick behind.** See below |
| `shots_fired` | int | spray index; resets between bursts, so it identifies bullet 1 vs bullet 12 |
| `punch_yaw`, `punch_pitch` | float | recoil kick applied to the view |
| `is_ducking`, `is_walking`, `is_airborne`, `is_scoped` | 0/1 | stance |
| `health`, `armor` | int | |
| `is_alive` | 0/1 | |
| `flash_remaining` | float | seconds of blindness left |
| `active_weapon` | string | e.g. `AK-47`; empty when holding nothing |
| `place` | string | named map area, e.g. `Palace`; empty when unknown |

### buttons bitmask

```
0x1    attack        0x200    move left      0x10000   speed (walk)
0x2    jump          0x400    move right     0x2000    reload
0x4    duck          0x800    attack2
0x8    forward       0x80     turn left
0x10   back          0x100    turn right
```

A counterstrafe is `move left` released and `move right` tapped (or the reverse)
within a few ticks, with `speed` collapsing toward zero. Both bits plus `speed`
plus `shots_fired` are on the same row.

## rounds.csv

| Column | Meaning |
|---|---|
| `number` | 1-based |
| `start_tick`, `freeze_end_tick`, `end_tick`, `official_end_tick` | phase boundaries |
| `winner` | 2 = T, 3 = CT |
| `reason` | demoinfocs `RoundEndReason` (1 = bombed, 7 = defused, 8 = CT win, 9 = T win) |
| `timeout_before` | 1 if a tactical timeout preceded this round |
| `timeout_team` | which team called it |
| `complete` | 0 if the demo ended before this round officially ended |
| `tick_rows` | rows this round contributed |

**A timeout inflates freezetime.** Timeouts sit *inside* the following round's
freezetime, not between rounds. Timeout rounds in the reference demo have
freezetime spans of 7,378 and 3,755 ticks against 1,280–1,696 normally. Those
extra rows are all `phase = 'freeze'`, so anything filtering to `live` is
unaffected — but a freezetime-duration analysis must exclude them.

**`official_end_tick = 0` is a sentinel** meaning the demo ended before that
round officially closed. Expect it on the final round of most demos.

## round_players.csv

One row per `(round, steamid)`. Guaranteed to be a **superset** of the players
appearing in `ticks.csv.gz` for that round, so an inner join never silently
drops tick rows.

| Column | Meaning |
|---|---|
| `money_at_freeze_end`, `equip_value_at_freeze_end` | economy entering the round |
| `survived` | alive when the win condition was met |
| `disconnected` | dropped mid-round — distinguishes this from being killed |
| `joined_late` | appeared after freezetime, so economy is zeroed, not measured |

`survived = 1` with a death later in the tick stream is correct, not a bug: the
player was alive at `RoundEnd` and died during `postround`.

## manifest.json

Records `map`, `tick_rate`, `rounds`, `tick_rows`, `schema_version`, the full
column list per file, and two honesty flags worth checking before trusting a run:

- **`tick_rate_source`** — `measured` if read from the demo's `ServerInfo`,
  `assumed` if the demo never reported one and a default was used. Every
  velocity in the file scales with this number, so an `assumed` run is one whose
  speeds you should not compare against a `measured` one.
- **`complete`** — false if any round was truncated. Note this is routinely
  false on a normal demo, because demos typically end before the last round's
  `RoundEndOfficial`; check `rounds.csv` to see which round is affected.

## Schema evolution

`schema_version` is `major.minor`. Appending a trailing column bumps minor and
stays readable by header-aware consumers (DuckDB, pandas). Removing or
reordering columns bumps major. Read the manifest's `columns` map rather than
assuming positions.

Known change so far: `max_speed` existed in early drafts and was removed. It was
constant 260 for every weapon — CS2 does not network a weapon-adjusted speed cap
at all. To normalize speed by weapon, join `active_weapon` against a table you
maintain.

## Known limitation

The row-production path has no unit tests — it needs a live parser, and mocking
was ruled out. Every serious defect found during development lived there and was
caught by querying the artifact, not by the test suite. If you extend this tool,
validate against real output: primary-key uniqueness, roster ⊇ tick
participants, no player whose entire round sits at one position, no eco round
reporting rifle-priced equipment.
